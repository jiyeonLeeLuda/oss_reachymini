## 1단계 — 개념 지도와 핵심 3개

2·3주차에 등장하는 개념들을 모아 군집화하면 5개 덩어리가 나온다:

```
A. 공간 표현 — "어디로"
   ├─ 포즈(pose) = 위치(x,y,z) + 자세(roll, pitch, yaw)
   ├─ create_head_pose, 좌표계, 변환 행렬
   └─ 작업 공간(머리 포즈) vs 관절 공간(모터 각도)

B. 시간 표현 — "어떤 길로, 어떤 속도로"
   ├─ 궤적(trajectory) = 시간에 따른 포즈의 연속
   ├─ 보간: linear / minjerk / ease / cartoon
   └─ 매개변수 방정식 (8자 패턴), duration

C. 실행 모델 — "누가 기다리고 누가 돌리나"
   ├─ goto_target (블로킹: 끝날 때까지 대기)
   ├─ set_target (비블로킹: 목표만 갱신, 루프는 내 코드)
   └─ 동시 다중 부위 제어, 동작 시퀀스

D. 기구학 — "포즈를 모터가 어떻게 만드나"
   ├─ 스튜어트 플랫폼: 모터 6개 → 머리 6자유도
   └─ 역기구학 IK (포즈→각도) / 정기구학 FK (각도→포즈)

E. 하드웨어 상태와 안전
   ├─ 토크 on/off (컴플라이언트 모드)
   └─ 온도·부하 모니터링, 안전 동작 범위
```

### 핵심 3개

1. **포즈 = 위치 3 + 자세 3, 합쳐서 6자유도(6-DOF)** — A의 전부이고, D는 "이 6개
   숫자를 모터 6개가 어떻게 실현하나"라는 질문이므로 D의 입구이기도 하다.
   과제 4(스튜어트 플랫폼)가 여기서 풀린다.
2. **궤적 = 포즈의 시간 함수이고, 보간은 출발점과 도착점 사이를 채우는 방법** —
   B의 전부. 8자 과제, 보간 비교 과제가 전부 이 한 문장의 변주다.
3. **블로킹 vs 비블로킹 실행 모델** — `goto_target`은 궤적을 만들어 다 따라갈
   때까지 내 코드를 세워두고, `set_target`은 목표만 던지고 즉시 돌아와서 루프를
   내가 돈다. C의 전부이고, E(모니터링하면서 움직이기)와 DeskMate의 DoA 추적이
   왜 비블로킹이어야 하는지가 여기서 풀린다.

이 3개만 잡으면 과제는 전부 조합 문제가 된다:
8자 과제 = ①+② / 보간 과제 = ② / 끄덕이기 시퀀스 = ①+③ /
안전 제어 = ③+E / 스튜어트 과제 = ①+D

## 2단계 — 실제 예시로 감 잡기

### ① 포즈 (위치 3 + 자세 3)

비유가 필요 없는 게, 내 머리가 그대로 예시다. 거울 앞에서:

- "네" 할 때 고개 끄덕 — **pitch**
- "아니요" 도리도리 — **yaw**
- 갸우뚱 — **roll**

이 셋은 머리의 *방향*만 바꾼다. 이제 방향은 그대로 두고 목을 거북이처럼 앞으로
빼거나, 움츠려서 내리거나 — 이게 x, z 같은 *위치* 이동. 로봇 머리도 정확히 같은
6개 숫자로 기술된다. Peekaboo에서 `PEEK_Z_MM`으로 머리를 내린 건 위치의 z를,
좌우 갸웃은 자세의 roll을 만진 것.

### ② 궤적과 보간

엘리베이터가 1층에서 5층 가는 것 — 비유가 아니라 보간 그 자체(위치가 시간에 따라
변하는 것). 출발하자마자 최고 속도로 가다가 5층에서 뚝 멈추면 승객이 휘청한다 —
이게 **linear**. 실제 엘리베이터는 서서히 가속했다가 서서히 감속해서 도착한다 —
이게 **ease/minjerk**. 같은 출발점, 같은 도착점, 같은 소요 시간이어도 *중간을
어떻게 채우느냐*가 다르고, 로봇에선 그게 "기계 같다 vs 자연스럽다"의 차이가 된다.

### ③ 블로킹 vs 비블로킹

실제 코드 두 조각:

```python
# 블로킹: 이 줄에서 내 프로그램은 2초간 멈춰 있음
mini.goto_target(head=pose, duration=2.0)
print("이 줄은 2초 뒤에 실행됨")

# 비블로킹: 매 루프마다 목표를 갱신, 내 코드가 계속 돎
while True:
    pose = 지금_이_순간_머리가_있어야_할_위치_계산(time.time())
    mini.set_target(head=pose)   # 즉시 반환
    time.sleep(0.02)             # 50Hz 루프
```

차이가 드러나는 순간은 "움직이는 **도중에** 뭔가 해야 할 때". 2초짜리
`goto_target`이 도는 동안엔 소리가 나도, 온도가 치솟아도, 중지 버튼이 눌려도
내 코드는 모른다. 비블로킹 루프는 매 0.02초마다 내 코드로 돌아오니까 그때그때
반응할 수 있다.

## 3단계 — 문제 풀이 (개념당 5문제, 하나씩 진행)

> 진행 방식: 문제를 하나 풀면 다음 문제가 나온다. 막히면 힌트를 받거나
> 조건을 조절한 쉬운 문제로 바꾼다. 틀리면 어떤 오개념 때문인지 디버깅한다.
> 마지막에 모범 답안 worked example + cognitive task analysis.

### [개념① 포즈 — 문제 1] ✅ 통과

로봇이 **"아니요" 하듯 고개를 왼쪽으로 돌렸다가 오른쪽으로 돌리는** 동작을
만들려고 한다. 6개 자유도(x, y, z, roll, pitch, yaw) 중 **무엇을 움직여야 할까?**
그리고 Peekaboo의 "좌/우 갸웃"과는 어떻게 다른지 한 문장으로 설명해보기.

> **내 답**: yaw가 도리도리(작업 공간/머리의 자유도)이고, Peekaboo의 갸웃은
> roll + z축 제어가 함께 이루어진 것.
>
> **피드백**: 정답. 갸웃을 roll 단일이 아닌 roll+z 조합으로 분해한 것이 핵심 —
> 포즈를 6개 성분으로 쪼개 읽는 눈. "작업 공간의 자유도"라는 구분은 개념④
> 기구학("모터 각도는 관절 공간")으로 이어진다.

### [개념① 포즈 — 문제 2] ← 현재 진행 중

다음 코드를 실행하면 로봇 머리가 어떤 동작을 할지 순서대로 예측하기:

```python
mini.goto_target(head=create_head_pose(z=-30, mm=True), duration=1.0)
mini.goto_target(head=create_head_pose(z=-30, pitch=20, mm=True), duration=1.0)
mini.goto_target(head=create_head_pose(), duration=1.0)
```

특히 **두 번째 줄에 z=-30이 또 들어 있는 이유**와 **세 번째 줄(인자 없음)의
의미**를 포함해서 답하기.

> **내 답(1차)**: 머리가 아래로 내려가고(1초), pitch 끄덕끄덕 후 다시 z=-30으로
> 돌아가고, 세 번째 줄은 기본값 복귀. (mm은 모르겠음)
>
> **디버깅**:
> - 맞음 — 1줄(하강), 3줄(중립 복귀). `mm=True`는 단위 지정(밀리미터; 없으면 SI 단위).
> - 버그① "끄덕끄덕": `goto_target`은 제스처가 아니라 **목표 포즈 1장**을 받는다.
>   `pitch=20` = "20도 숙인 상태로 가서 멈춰라". 왕복은 goto 여러 번.
>   → 포즈 = 사진 한 장, 동작 = 사진의 연속.
> - 버그② "다시 z=-30으로 복귀": 인자는 상대 변화량이 아니라 **절대 목표 상태**.
>   2줄의 z=-30은 "내려간 자세를 유지한 채 pitch를 추가"하기 위해 반복 명시한 것.
> - 정답 시퀀스: ① 30mm 하강 → ② 내려간 채로 pitch 20도 → ③ 중립 복귀.
>
> **되물음(통과 조건)**: 2줄에서 z=-30을 빼고 `create_head_pose(pitch=20, mm=True)`만
> 쓰면 로봇은 어떻게 움직일까?

> **되물음 답**: +30이 되어 올라옴 (✅ 관찰 결과 정확).
> 단, "-30이 두 번이니 같은 방향으로 두 번 가나?"에서 상대값 모델이 재발견됨.
>
> **최종 교정**: 인자는 "가야 할 좌표"(절대)이지 "이동량"(상대)이 아니다.
> 엘리베이터 "5층" 버튼을 두 번 눌러도 10층에 가지 않는 것과 동일 — 이미
> z=-30이면 z=-30 재명령 시 z는 안 움직이고 pitch만 변한다.
> 한 줄 요약: `z=-30` = "좌표 -30에 있어라"(상태 선언) ≠ "30 내려가라"(이동 명령).

### [개념① 포즈 — 문제 3] ← 현재 진행 중

읽기에서 쓰기로. 로봇이 **숨어 있다가(z=-30), "왼쪽으로 15도 갸웃한 채로"
원래 높이까지 올라오는** 까꿍 동작. 빈칸 채우기:

```python
# 숨기
mini.goto_target(head=create_head_pose(z=-30, mm=True), duration=1.0)

# 까꿍: 갸웃한 채로 올라오기 (한 번의 goto_target으로)
mini.goto_target(head=create_head_pose(______________), duration=0.8)
```

포인트: 갸웃은 roll인가 yaw인가 / 부호·각도는 / **z는 써야 하나 생략해야 하나?**

> **내 답**: `roll=15, z=0, mm=True` ✅ 통과
>
> **피드백**: z=0 명시 = 절대 좌표 사고의 정확한 적용 (생략해도 기본값 0으로 동일
> 동작 — 명시가 의도 전달에 더 좋음). roll 부호의 좌/우 방향은 좌표계 규약
> 문제라 시뮬에서 확인이 정석 (Peekaboo는 random.choice로 양쪽 선택).
> 핵심 관찰: 한 goto에 z=0과 roll=15를 같이 넣으면 "올라간 뒤 갸웃"이 아니라
> **올라가면서 동시에 갸웃** — 보간이 6개 성분을 동시에 채우기 때문. (개념②의 다리)

### [개념① 포즈 — 문제 4] ← 현재 진행 중

머리 상태 표현에 왜 위치(x,y,z) 3개로는 부족한가? **위치는 완전히 같은데
자세가 달라서 다르게 보이는** 실제 상황을 하나 들어 설명하기.
(로봇이든 일상 물건이든 OK, 문제 1~3의 예시 재사용 금지)

> **내 답(1차)**: 좌표는 이동할 점을 명시할 뿐, 어떤 각도와 어떤 경로로 이동하는지에
> 따라 제스처를 표현할 수 있어서. 직선이동만으로는 부자연스러울 수 있음.
>
> **디버깅**: "각도"(자세 ✅)와 "경로/이동"(궤적 — 개념②의 주제 ❌)이 섞임.
> 버그의 정체 = **상태와 움직임의 혼동**. 포즈는 멈춰 있는 스냅샷(시간이 0인
> 세계)이라 "경로"가 등장할 수 없다. 경로·부드러움은 사진과 사진 *사이*를
> 채우는 보간의 이야기.
>
> **단순화 재출제**: 책상 위 정확히 같은 자리의 스마트폰 사진 2장 — 화면이
> 천장을 보는 것 vs 엎어진 것. 두 사진에서 위치(x,y,z)는 같은가 다른가?
> 두 상태를 구분하려면 어떤 숫자가 더 필요한가?
